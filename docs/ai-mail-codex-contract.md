# #37 Codex service and #38 caller contract

The Main-owned service launches only an explicitly provisioned executable selected by `HANTONG_CODEX_EXECUTABLE`, resolved inside Electron's app-owned data directory. It never searches `PATH` or reads the user's global Codex home. Authentication and app-server data use a marked, owner-only Hantong home and an empty app-owned workspace; the child receives a restricted environment with no inherited credentials. The only supported login method is the official `account/login/start` request with `{ type: 'chatgpt', codexStreamlinedLogin: true }`, opened in the system browser after validating the HTTPS auth host. Status is connected only when `account/read` confirms `type: 'chatgpt'`.

The renderer contract remains `getAiMailCodexStatus()`, `connectAiMailCodex()`, `disconnectAiMailCodex()`, `generateAiMailDraft(request)`, and `cancelAiMailGeneration(requestId)`. Generation requests include explicit account, compose, request, and generation identifiers, plus bounded plain-text prompt and optional follow-up. Results are plain text with token counts or a bounded error; callers render successful text as untrusted content. Request ownership is the tuple `(accountId, composeId, requestId, generation)`: retries increment `generation`, compose/account changes invalidate earlier ownership, and cancellation names the request. The current service intentionally sends no model turn and reports `tool_restrictions_unverified`; request/result and cancellation execution remain unimplemented until restrictions pass the gates below. Callers must never pass Gmail content until an independently approved product flow permits it. Main does not access Gmail content in this service.

Each app-owned CODEX_HOME is initialized with `project_doc_max_bytes = 0`, an app-owned `default_permissions = "hantong-no-local-io"` profile, a filesystem root deny, read-only access to the empty private workspace, and network disabled. An existing marked home is reused only if its private `config.toml` exactly matches this managed configuration; unrelated config is rejected. CLI flags request optional capabilities off, and the app-server client rejects every server-initiated request, including approval/tool requests. These are defense-in-depth settings, not proof that model-visible tools are absent or that macOS enforces the custom profile correctly.

The installed official 0.167.1 v2 schemas and tagged source distinguish several controls; they do not expose one all-tools-off or tool-allowlist request field. `thread/start.sandbox` supports `read-only`, and `turn/start.sandboxPolicy` supports sandbox overrides; `approvalPolicy: "never"` controls approvals and does not suppress tool registration. The supported `default_permissions`/`[permissions.<id>]` configuration profiles can select a sandbox policy, and thread responses expose `activePermissionProfile` provenance. Feature flags include `shell_tool`; `unified_exec` is a separate command-execution backend, and the #35 runtime reported it enabled even after the disable request. The service requests known feature disables and inspects tool-related flags/inventories, but it does not treat those flags as proof that all built-ins are unavailable. This decision uses the complete schema/source/runtime evidence, not the absence of one API field.

The two #35 reports are different test runs and should not be collapsed. The earlier 0.167.0 run completed synthetic `gpt-6-luna` generation, cancellation, and retry under the named custom profile; it observed no tool item in those turns, `shell_tool=false`, no MCP/callable apps, and the expected profile name. That establishes a bounded generation outcome and those observations, but a clean turn with no tool event does not prove that tools were unavailable or that filesystem/network policy was enforced. The later profile-control run attempted `/bin/echo` under the restrictive profile, `/bin/cat` on a denied canary, `/bin/cat` on an explicitly allowlisted canary, and a built-in read-only echo control. All four returned exit 71 with sandbox denial, including the harmless and allowlisted positive controls; `thread/start` with that custom profile failed JSON-RPC `-32603`/sandbox, while built-in read-only `thread/start` succeeded but allowed reads. Thus the Mac profile backend failed both positive and negative controls, so its denial result is inconclusive. Do not enable generation until a supported product runtime can start the selected profile and demonstrate successful harmless/allowed controls, denied out-of-scope access, no network, and safe synthetic turns under the same pinned build.

Accordingly, generation and cancellation remain fail-closed with `tool_restrictions_unverified`; no request is sent to a model. Account connection and ChatGPT login can proceed independently when a product-owned executable is available. The protocol diagnostics are not a substitute for those runtime controls.

Connection controls and login/logout are product-owned but require an explicitly provisioned Hantong Codex executable; no packaged executable or provisioning approval is included in #37. Until it exists, status is `unsupported/product_owned_executable_unavailable`. Proposed release pin and layout: official standalone `codex-cli 0.167.1` for `aarch64-apple-darwin`, from the OpenAI [`rust-v0.167.1` GitHub release](https://github.com/openai/codex/releases/tag/rust-v0.167.1), asset `codex-aarch64-apple-darwin.tar.gz` (104 MB; published SHA-256 `4c97fbdafba21e172254107939489691195f34712cf0cb31293e5e21be8f5bfa`), vendored at `resources/codex/0.167.1/aarch64-apple-darwin/bin/codex`, then copied by Electron Builder `extraResources` to `Contents/Resources/codex-runtime/bin/codex`. Packaged Main should resolve only from `process.resourcesPath/codex-runtime/bin/codex`, verify the packaged file/hash/signature before spawn, and keep CODEX_HOME under the app's private user-data directory. The official [`@openai/codex` 0.167.1 package listing](https://www.npmjs.com/package/@openai/codex) identifies Apache-2.0 licensing; bundling must carry the required license/notice material and verify the release archive's own contents before approval. The current development hook remains explicit `HANTONG_CODEX_EXECUTABLE` at `userData/codex-runtime/bin/codex`; neither path discovery nor runtime download is allowed. The exact external action still requiring manager approval is a one-time build-time download of that named 104 MB release asset, SHA-256 verification, archive/license review, and inclusion of the extracted executable and notices in Hantong's signed macOS bundle; this work did not download/install it. No cloud/account setting change was made.

The installed official app-server 0.167.1 schema confirms `account/login/start`, `account/login/cancel`, `account/read`, `account/logout`, `thread/start`, `turn/start`, and `turn/cancel`. It also confirms `thread/start.sandbox`, `turn/start.sandboxPolicy`, `approvalPolicy`, and response `activePermissionProfile`; the installed generated schema has no client-supplied tool list on thread or turn start. Recheck official schema/source and all isolation controls whenever the bundled executable changes. Synthetic fixtures only; no live Gmail prompt or data. Current isolated builds can expose account controls only when launched with a product-owned executable already provisioned; they cannot generate drafts.
