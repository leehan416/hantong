# #37 Codex service and #38 caller contract

The Main-owned service launches only `Contents/Resources/codex-runtime/bin/codex` from Electron's packaged resources, never a `PATH` or launcher/environment override. It verifies an immutable build-owned version/target/SHA-256 pin, regular non-symlink file and directory identities, permissions, and file identity again before spawn. The pinned executable is official OpenAI Codex CLI 0.167.1 for `aarch64-apple-darwin`; its executable SHA-256 is `ebabe5f0d79145a9e61274ce9ecf7c02c9021b7b04bfa59b7e61ad4461c32b0b`. The local build artifact is provisioned at `resources/codex-runtime/bin/codex` (ignored by Git) and packaged as `Contents/Resources/codex-runtime/bin/codex`. Authentication and app-server data use a marked, owner-only Hantong home and an empty app-owned workspace; the child receives a restricted environment with no inherited credentials. The only supported login method is the official `account/login/start` request with `{ type: 'chatgpt', codexStreamlinedLogin: true }`, opened in the system browser after validating the HTTPS auth host. Status is connected only when `account/read` confirms `type: 'chatgpt'`; live account login has not been performed or verified.

The renderer contract remains `getAiMailCodexStatus()`, `connectAiMailCodex()`, `disconnectAiMailCodex()`, `generateAiMailDraft(request)`, and `cancelAiMailGeneration(requestId)`. Generation requests include explicit account, compose, request, and generation identifiers, plus bounded plain-text prompt and optional follow-up. Results are plain text with token counts or a bounded error; callers render successful text as untrusted content. Main owns each app-server thread by `(accountId, composeId)` and each in-flight turn by `(accountId, composeId, requestId, generation)`. Older generations are rejected, superseded turns are interrupted, and late notifications are ignored after ownership is removed. Prompt and follow-up character and UTF-8 byte sizes are bounded. The protocol lifecycle streams assistant deltas, captures token counts when available, reports failures and timeouts, and uses the supported `turn/interrupt` method; no Gmail data enters this service. Generation remains blocked until the connected pinned app-server confirms the profile in `config/read`, `permissionProfile/list` marks it allowed, an ephemeral thread returns read-only/no-network sandbox plus `approvalPolicy: never`, known tool-related feature switches are disabled, MCP/callable-app inventories are empty, and project-doc bytes are zero. Main then exercises the effective profile through `command/exec` using unique synthetic canaries: echo and workspace read must succeed, while a read outside the allowlisted workspace must fail without revealing its marker. Canaries and the temporary thread are removed even on failure. No model turn or renderer-supplied attestation is involved in policy readiness.

Each app-owned CODEX_HOME is initialized with `project_doc_max_bytes = 0`, an app-owned `default_permissions = "hantong-no-local-io"` profile, a filesystem root deny, read-only access to the empty private workspace, and network disabled. An existing marked home is reused only if its private `config.toml` exactly matches this managed configuration; unrelated config is rejected. CLI flags request optional capabilities off, and the app-server client rejects every server-initiated request, including approval/tool requests. The no-login native canary checks confirm the pinned runtime applies the filesystem boundaries under the expected profile; this does not prove that model-visible tools are absent or establish model behavior.

The installed official 0.167.1 v2 schemas and tagged source distinguish several controls; they do not expose one all-tools-off or tool-allowlist request field. `thread/start.sandbox` supports `read-only`, and `turn/start.sandboxPolicy` supports sandbox overrides; `approvalPolicy: "never"` controls approvals and does not suppress tool registration. The supported `default_permissions`/`[permissions.<id>]` configuration profiles can select a sandbox policy. `activePermissionProfile` is part of `ThreadSettings` (and its settings-updated notification), not the `thread/start` response. Feature flags include `shell_tool`; the installed runtime still reports `unified_exec` enabled even after the disable request. The service does not treat feature flags as proof that all built-ins are unavailable; it gates generation on successful filesystem controls under the effective app-server profile instead.

The two #35 reports are different test runs and should not be collapsed. The earlier 0.167.0 run completed synthetic `gpt-6-luna` generation, cancellation, and retry under the named custom profile; it observed no tool item in those turns, `shell_tool=false`, no MCP/callable apps, and the expected profile name. That establishes a bounded generation outcome and those observations, but a clean turn with no tool event does not prove that tools were unavailable or that filesystem/network policy was enforced. The later profile-control run attempted `/bin/echo` under the restrictive profile, `/bin/cat` on a denied canary, `/bin/cat` on an explicitly allowlisted canary, and a built-in read-only echo control; its exit 71 results alone were inconclusive. A fresh 0.167.1 no-login app-server run with synthetic private CODEX_HOME and canaries returned echo exit 0, denied canary exit 1 without its marker, and allowlisted canary exit 0 with its marker when run outside the outer execution sandbox. The installed server reported `shell_tool=false`, `unified_exec=true`, no MCP servers or installed apps, the configured profile allowed, `project_doc_max_bytes=0`, and a `thread/start` response with read-only/no-network sandbox and `approvalPolicy=never`. This confirms the native filesystem boundaries and current gate inputs; no model turn or user account was exercised.

Generation and cancellation remain fail-closed with `tool_restrictions_unverified` until the service's live no-login readiness checks succeed; this diagnostic task sent no model request. Account connection and ChatGPT login can proceed independently when a product-owned executable is available. Model behavior and live account acceptance remain unverified.
