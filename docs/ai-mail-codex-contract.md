# #37 Codex service and #38 caller contract

The Main-owned service launches only `Contents/Resources/codex-runtime/bin/codex` from Electron's packaged resources, never a `PATH` or launcher/environment override. It verifies an immutable build-owned version/target/SHA-256 pin, regular non-symlink file and directory identities, permissions, and file identity again before spawn. The pinned executable is official OpenAI Codex CLI 0.167.1 for `aarch64-apple-darwin`; its executable SHA-256 is `ebabe5f0d79145a9e61274ce9ecf7c02c9021b7b04bfa59b7e61ad4461c32b0b`. The local build artifact is provisioned at `resources/codex-runtime/bin/codex` (ignored by Git) and packaged as `Contents/Resources/codex-runtime/bin/codex`. Authentication and app-server data use a marked, owner-only Hantong home and an empty app-owned workspace; the child receives a restricted environment with no inherited credentials. The only supported login method is the official `account/login/start` request with `{ type: 'chatgpt', codexStreamlinedLogin: true }`, opened in the system browser after validating the HTTPS auth host. Status is connected only when `account/read` confirms `type: 'chatgpt'`; live account login has not been performed or verified.

The renderer contract remains `getAiMailCodexStatus()`, `connectAiMailCodex()`, `disconnectAiMailCodex()`, `generateAiMailDraft(request)`, and `cancelAiMailGeneration(requestId)`. Generation requests include explicit account, compose, request, and generation identifiers, plus bounded plain-text prompt and optional follow-up. Results are plain text with token counts or a bounded error; callers render successful text as untrusted content. Request ownership is the tuple `(accountId, composeId, requestId, generation)`: retries increment `generation`, compose/account changes invalidate earlier ownership, and cancellation names the request. The current service intentionally sends no model turn and reports `tool_restrictions_unverified`; request/result and cancellation execution remain unimplemented until restrictions pass the gates below. Callers must never pass Gmail content until an independently approved product flow permits it. Main does not access Gmail content in this service.

Each app-owned CODEX_HOME is initialized with `project_doc_max_bytes = 0`, an app-owned `default_permissions = "hantong-no-local-io"` profile, a filesystem root deny, read-only access to the empty private workspace, and network disabled. An existing marked home is reused only if its private `config.toml` exactly matches this managed configuration; unrelated config is rejected. CLI flags request optional capabilities off, and the app-server client rejects every server-initiated request, including approval/tool requests. These are defense-in-depth settings, not proof that model-visible tools are absent or that macOS enforces the custom profile correctly.

The installed official 0.167.1 v2 schemas and tagged source distinguish several controls; they do not expose one all-tools-off or tool-allowlist request field. `thread/start.sandbox` supports `read-only`, and `turn/start.sandboxPolicy` supports sandbox overrides; `approvalPolicy: "never"` controls approvals and does not suppress tool registration. The supported `default_permissions`/`[permissions.<id>]` configuration profiles can select a sandbox policy, and thread responses expose `activePermissionProfile` provenance. Feature flags include `shell_tool`; `unified_exec` is a separate command-execution backend, and the #35 runtime reported it enabled even after the disable request. The service requests known feature disables and inspects tool-related flags/inventories, but it does not treat those flags as proof that all built-ins are unavailable. This decision uses the complete schema/source/runtime evidence, not the absence of one API field.

The two #35 reports are different test runs and should not be collapsed. The earlier 0.167.0 run completed synthetic `gpt-6-luna` generation, cancellation, and retry under the named custom profile; it observed no tool item in those turns, `shell_tool=false`, no MCP/callable apps, and the expected profile name. That establishes a bounded generation outcome and those observations, but a clean turn with no tool event does not prove that tools were unavailable or that filesystem/network policy was enforced. The later profile-control run attempted `/bin/echo` under the restrictive profile, `/bin/cat` on a denied canary, `/bin/cat` on an explicitly allowlisted canary, and a built-in read-only echo control; its exit 71 results alone were inconclusive. A fresh 0.167.1 run with a new synthetic private CODEX_HOME distinguished the host layers: outside escalation, direct outer echo/cat controls succeeded but Codex's nested `sandbox-exec` failed each command with `sandbox_apply: Operation not permitted`; through normal approved escalation, the same commands under the same profiles produced restrictive-profile echo exit 0, denied canary read exit 1/`Operation not permitted` without revealing its contents, allowlisted canary read exit 0 with the synthetic marker, and built-in read-only echo exit 0. `permissionProfile/list` reported both test profiles allowed, and a no-generation `thread/start` returned active profile `hantong-no-local-io` with no parent. This confirms the supported macOS profile can enforce the tested command/read boundaries when the outer Codex execution sandbox is not preventing nested Seatbelt setup; it does not prove model-visible tool inventory or a turn's behavior. Continue to keep generation disabled until a separate authorized synthetic turn confirms the pinned app-server uses this default profile and the shell feature/tool registry is restricted as expected.

Generation and cancellation remain fail-closed with `tool_restrictions_unverified`; this diagnostic task sent no model request. Account connection and ChatGPT login can proceed independently when a product-owned executable is available. The protocol diagnostics are not a substitute for the future synthetic-turn check.

Connection controls can launch the product-owned runtime when the local provisioning artifact is present; packaging configuration copies `resources/codex-runtime` to `Contents/Resources/codex-runtime`. The official standalone Codex CLI 0.167.1 for `aarch64-apple-darwin` came from the OpenAI [`rust-v0.167.1` GitHub release](https://github.com/openai/codex/releases/tag/rust-v0.167.1), asset `codex-aarch64-apple-darwin.tar.gz`. Its published archive SHA-256, `4c97fbdafba21e172254107939489691195f34712cf0cb31293e5e21be8f5bfa`, was verified against downloaded bytes; the separate executable SHA-256 is `ebabe5f0d79145a9e61274ce9ecf7c02c9021b7b04bfa59b7e61ad4461c32b0b`. The reproducible `npm run provision:codex-runtime` script enforces the pinned checksums, accepts only a bounded HTTPS redirect chain to GitHub release asset hosts, inspects the archive before extraction, and installs the executable into the ignored resource path. The official Codex repository release is Apache-2.0 licensed; its license is included at `resources/codex-runtime/LICENSE` and packaged with the runtime, with source attribution in `THIRD_PARTY_NOTICES.md`. `npm run build:unpack` completed with exit code 0 and produced `dist/mac-arm64/Hantong.app`; the configured self-signed identity was used and notarization was explicitly skipped. This confirms the local unpacked packaging step, not a Developer ID signed/notarized distribution release. The pin and bundle are prepared, while live login, model behavior, runtime tool-policy verification and distribution signing/notarization remain unverified. No live account, cloud setting or Gmail data/action was used.

It also confirms `thread/start.sandbox`, `turn/start.sandboxPolicy`, `approvalPolicy`, and response `activePermissionProfile`; the installed generated schema has no client-supplied tool list on thread or turn start.
